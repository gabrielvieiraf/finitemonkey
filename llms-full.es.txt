Finite Monkey es un plugin de Claude Code para quien construye con un agente de IA y quiere que el resultado se sostenga. El trabajo termina hecho y comprobado sobre los archivos tal como están ahora. Aprovecha el código que el proyecto ya tiene, queda lo bastante limpio para seguir cambiándolo, parte de preguntas hechas y fuentes leídas antes de la primera línea, y se queda dentro de lo que puedes juzgar.

Funciona con hooks y comprobaciones que actúan aunque el modelo no se acuerde de ellos. Lo instalas una vez y sigues trabajando como ya trabajas, sin comandos que memorizar. Los mismos hábitos sirven para investigación, escritura y decisiones que tomas con IA, también fuera del código.

```sh
npx finitemonkey init
```

El plugin, los requisitos y las versiones previas están en [Instalación](#instalación).

## Qué cambia cuando construyes con él

- **Terminado significa comprobado.** Cada tarea tiene una definición de terminado, y Finite Monkey la ejecuta por sí mismo antes de que la sesión pueda cerrarse. [El control](#el-control-terminado-significa-comprobado)
- **Nada que no puedas recuperar.** Los tests, los secretos, el historial de git y producción quedan protegidos antes de que se ejecute cada comando. [Guardas](#guardas-tests-secretos-git-y-producción)
- **Reutilizar antes de escribir.** Cuando el agente define algo que el proyecto ya tiene, se le dice dónde está lo que ya existe. [Reutilización y código limpio](#reutilización-y-código-limpio)
- **Código que sigue limpio.** El código tocado no pasa de los límites de tamaño, complejidad y duplicación, y los tics de código de IA se retienen al final. [Reutilización y código limpio](#reutilización-y-código-limpio)
- **Pensar antes de construir.** Una tarea de verdad empieza con una propuesta corta y las pocas preguntas que cambian la respuesta. La investigación guarda fuentes fechadas, y las decisiones quedan por escrito con un camino de vuelta. [Piensa antes de construir](#piensa-antes-de-construir)
- **Aprender por el camino.** Finite Monkey guarda lo que demostraste saber, por concepto, y dibuja dónde cayó el trabajo aceptado respecto a eso. [Aprende mientras construyes](#aprende-mientras-construyes-dónde-cayó-tu-trabajo)
- **El producto entero.** Un plano lista lo que necesita un SaaS o una landing page de verdad y qué elementos ya están en verde. [Lo que un producto de verdad todavía necesita](#lo-que-un-producto-de-verdad-todavía-necesita)
- **Varios agentes a la vez.** Cada uno tiene su worktree, y un tablero los muestra a todos. [Varios agentes a la vez](#varios-agentes-a-la-vez)
- **Más allá del código.** La investigación, la escritura y las decisiones pasan por las mismas comprobaciones. [Una forma de pensar con IA](#no-es-solo-para-código-una-forma-de-pensar-con-ia)

## El control: "terminado" significa comprobado

<p align="center"><img src="https://raw.githubusercontent.com/gabrielvieiraf/finitemonkey/next/assets/gate.gif" width="760" alt="Grabación de terminal. finitemonkey gate ejecuta el contrato de la tarea: el test total rounds to cents falla y el control responde no terminado. El código se corrige para redondear el total, se hace commit y el control se ejecuta de nuevo: 15 aprobadas, 0 fallos, terminado."></p>

- Cada tarea tiene una **definición de terminado** que una máquina puede comprobar: comandos que deben salir bien, tests que deben existir y pasar, un diff que no se sale del alcance.
- Cuando Claude intenta cerrar la sesión, el hook `Stop` ejecuta ese contrato. Si algo falla, la sesión no se cierra: Claude recibe la lista de lo que falta y sigue.
- Solo cuenta como prueba lo que Finite Monkey ejecutó por sí mismo, sobre el árbol actual. "Ejecuté los tests antes de mi último cambio" no vale.
- El informe final sale solo de esas pruebas: verificado, no verificado, pendiente.

## Guardas: tests, secretos, git y producción

<p align="center"><img src="https://raw.githubusercontent.com/gabrielvieiraf/finitemonkey/next/assets/guards.gif" width="760" alt="Grabación de terminal del hook PreToolUse respondiendo a Claude Code. Borrar un archivo de test se deniega, escribir una clave de Stripe en un archivo de código se deniega, git push --force se deniega, y antes de git reset --hard se guarda una instantánea que finitemonkey undo lista."></p>

Cada llamada a una herramienta pasa por un hook `PreToolUse` antes de ejecutarse:

- **Los tests siguen siendo testigos.** Tests eliminados, `skip` u `only` nuevos, aserciones borradas y cambios en la configuración del propio control se deniegan. Cuando la suite solo pasa después de cambiar un test que ya existía, el control no lo da por verificado hasta que leas el cambio.
- **Los secretos nunca entran.** Una única regla de detección para archivos que se escriben, prompts, commits, historial y CI. Un hallazgo se informa por archivo y línea, nunca por su valor, con los pasos para rotarlo.
- **El trabajo en git nunca se pierde.** Una instantánea antes de cada operación arriesgada de git y un `undo` que la recupera. Nada de `--force`. Los worktrees con cambios pendientes se archivan en lugar de borrarse, y cada merge se comprueba para que no desaparezca nada de ningún lado.
- **Producción cambia por el camino de despliegue.** Los comandos con efecto sobre un servidor de producción se bloquean; el cambio pasa por el camino que declares.
- **Las reglas de tu CLAUDE.md se cumplen.** Las reglas que siempre deben valer se compilan en hooks, permisos, git hooks y pasos de CI, y `rules coverage` muestra, regla por regla, cuáles siguen siendo solo texto.

## Reutilización y código limpio

Un agente escribe rápido. Solo, agrega una segunda copia de una función que el proyecto ya tiene, y cada edición deja el archivo un poco más largo y más enredado. Finite Monkey sigue el código mientras se escribe:

- **Búscalo primero.** Cuando una edición define una función, clase o módulo con un nombre que el proyecto ya usa en otro lugar, se le dice al agente dónde está lo que ya existe. Antes de un módulo o una dependencia nueva, `guardian reuse` busca uno que ya cumpla ese papel. El registro guarda si cada aviso terminó en reutilización.
- **Límites en lo que tocas.** Al final, un archivo o una función que el cambio tocó no puede pasar de los límites de tamaño, complejidad cognitiva y anidamiento, sumar un ternario anidado, repetir líneas que existen en otro lugar ni crear un ciclo de imports. La deuda vieja que nadie tocó nunca bloquea.
- **Tics de código de IA.** Comentarios que narran el cambio, errores capturados y descartados, `any` sin motivo, salida de depuración, emoji en el código y un archivo nuevo junto al que debía editarse se retienen al final. Los nombres genéricos, los nombres con versión y los valores por defecto literales reciben un aviso. Solo tú puedes descartar un hallazgo, desde tu propia terminal.

## Piensa antes de construir

Casi todo lo que sale mal con un agente empieza antes del código: la pregunta que nadie hizo, la fuente que nadie abrió, la elección hecha antes de que las opciones estuvieran sobre la mesa.

- **Las preguntas que cambian la respuesta.** Un pedido lo bastante grande para ser una tarea, todavía sin contrato, recibe una propuesta corta antes de cualquier edición: el objetivo, el alcance, lo que existe hoy y cómo comprobar que está terminado, más como mucho unas pocas preguntas de opción múltiple, cada una con una recomendación. Cuando el agente acepta algo que dijiste sobre el código sin leer el código, te enteras.
- **Investiga con fuentes que se pueden comprobar.** `research new`, `research source` y `research status` guardan la pregunta, cada fuente con su fecha y lo que cambió, y cuándo parar. Una cita tiene que estar en la fuente que cita, un número tiene que venir de una fuente, y una cuestión abierta necesita los dos lados citados antes de que la respuesta cuente como terminada.
- **Decide con registro.** `decide new` escribe las opciones, los criterios escritos antes de los candidatos, "no hacer nada" como opción y el camino de vuelta. `inventory` escribe lo que existe hoy antes de reemplazar nada, y `cost` arma el modelo de costos de una API de pago o de un plan antes de que lo contrates.
- **Encuéntralo antes de adivinar.** La skill `retrieve` responde "dónde está" y "quién llama" a partir del código y de las afirmaciones registradas, con archivo y línea, y `map` guarda una línea por carpeta con lo que define.
- **Las vueltas tienen nombre.** El cuarto arreglo para el mismo error, el mismo archivo editado una y otra vez: Finite Monkey lo dice claro y retiene el cuarto intento.

## Aprende mientras construyes: dónde cayó tu trabajo

<p align="center"><img src="https://raw.githubusercontent.com/gabrielvieiraf/finitemonkey/next/assets/trajectory.gif" width="760" alt="Grabación de terminal de finitemonkey trajectory: un gráfico en colores por semana para el dominio backend, con bandas para lo hace solo, a ciegas con criterio, a ciegas sin criterio y más allá del horizonte, el trabajo aceptado marcado con puntos, un rebote marcado con una x y una marca de sostenido. Después signals blind-band informa que el 60 por ciento de la ayuda de horizonte salió sin criterio."></p>

El agente puede llevarte más allá de lo que puedes juzgar sin que ninguno de los dos lo note. Finite Monkey guarda la prueba de lo que demostraste saber, por concepto, y dibuja dónde cayó el trabajo aceptado semana a semana: lo que haces solo, lo que aceptaste a ciegas pero con un criterio que puedes comprobar, lo que aceptaste a ciegas sin ninguno y lo que estaba más allá del horizonte. Los rebotes (trabajo aceptado que volvió roto) y los arreglos que hiciste tú quedan marcados. El mismo gráfico es un panel dentro de Claude Code 2.1.287 o más nuevo.

El aprendizaje ocurre en el mismo ciclo. Un agente profesor, de solo lectura, explica un concepto al nivel que muestra tu cuaderno de conceptos, citando líneas de tu propio proyecto; cuando ya viste la explicación, hace una pregunta de predicción en su lugar. `teach` hace una pregunta cuya respuesta sale de ejecutar el ejemplo de la tarea, y `xray` muestra qué líneas cambiadas están dentro, en el borde o más allá de tu prueba. Vistas relacionadas: `signals blind-band` y `judge report`.

## Lo que un producto de verdad todavía necesita

<p align="center"><img src="https://raw.githubusercontent.com/gabrielvieiraf/finitemonkey/next/assets/blueprint.gif" width="760" alt="Grabación de terminal de finitemonkey planta saas: el plano de SaaS tiene 1 de 25 elementos, el siguiente es problema y público por escrito, seguido de la lista de elementos como cobros, webhooks de pago idempotentes, copia de seguridad probada y despliegue con vuelta atrás."></p>

Quien nunca puso un SaaS en marcha no sabe que necesita login, cobros, webhooks idempotentes, copias de seguridad y una forma de volver atrás. `planta saas` (o `planta landing`) lista lo que necesita una versión de verdad, comprueba qué elementos ya están en verde y nombra el siguiente con su mínimo, para que una pantalla de login no se llame producto.

## Varios agentes a la vez

<p align="center"><img src="https://raw.githubusercontent.com/gabrielvieiraf/finitemonkey/next/assets/fronts.gif" width="760" alt="Grabación de terminal: finitemonkey wt list muestra tres worktrees, uno por agente, cada uno con su rama, rango de puertos y propósito. finitemonkey fronts board muestra el control y el contrato de cada uno y una colisión: src/cart.ts cambiado en dos frentes."></p>

Cada frente de trabajo en paralelo tiene su worktree, rama y rango de puertos. `fronts board` muestra todos los frentes con su control y contrato en una sola pantalla y señala los archivos que dos frentes cambiaron, antes del merge. `fronts merge` integra los frentes informados con un merge que clasifica cada fragmento en conflicto y comprueba que no se perdió nada.

## No es solo para código: una forma de pensar con IA

Los hábitos de arriba tratan de cómo trabajas con una IA, así que valen tanto para un estudio de mercado, un informe o la elección de un proveedor como para un pull request:

- **Las afirmaciones se comprueban en su fuente.** Cuando un documento, un registro de decisión o un registro de investigación trae afirmaciones que dependen solo del modelo, Finite Monkey las lista. Cada una se comprueba en su fuente (`judge verify` comprueba que el DOI o la URL citada abre y contiene el fragmento citado), se corta o se entrega con lo que falta.
- **Texto que parece escrito por una persona.** La skill `write` y `prose check` señalan los patrones que un lector reconoce como escritos por una máquina, en un README, la descripción de un PR, las notas de una versión o una landing page.
- **Los mismos registros de investigación y de decisión.** `research` y `decide` no necesitan código: una pregunta con fuentes fechadas y criterios fijados antes de las opciones sirve para cualquier elección.
- **Sabe qué puedes juzgar, en cualquier área.** La prueba de lo que sabes se guarda por dominio, así que las mismas bandas valen para el trabajo que aceptas fuera del código.

La reutilización, el código limpio, las preguntas antes del trabajo, las vueltas y la comprobación de afirmaciones vienen encendidas por defecto (`level: standard`). `level: light` en `.finitemonkey/policy.yml` hace que solo observen y registren; `level: strict` enciende todo.

## Todo lo demás que hace

- **Pantallas y formularios.** `look` captura cada pantalla a 1440 y 390 px y revisa el orden del teclado, las etiquetas, los estados y los textos en lo que de verdad se renderiza.
- **El guardián del proyecto.** Las tareas recientes frente a los objetivos del proyecto: trabajo sin vínculo, alcance que crece, decisiones reabiertas, trabajo estancado y una previsión a partir de tus propias tareas anteriores.
- **Cadena de suministro y CI.** Lockfiles en orden, `osv-scanner`, CI y despliegue a la medida del proyecto, y `ci gate` ejecutando las mismas comprobaciones en cada pull request.
- **Costo.** Gasto del agente por tarea, día y mes frente a tus topes, y cuánto lleva costando cada contrato.

## Ningún comando que memorizar

Ejecutas un comando, una vez. A partir de ahí Finite Monkey actúa por contexto dentro de Claude Code:

- Los **hooks** hacen cumplir: `SessionStart` recupera el estado de la tarea, `UserPromptSubmit` detecta lo que pediste, `PreToolUse` frena la acción peligrosa antes de que ocurra, `Stop` no deja terminar mientras la definición de terminado falle, y `SubagentStop` revisa lo que informan los subagentes.
- Las **skills** las activa Claude por su cuenta cuando la situación lo pide: task, verify, look, finish.
- Los **comandos con barra** son atajos opcionales. Ningún flujo depende de que recuerdes uno.
- **El estilo de salida `report`** es opcional y viene apagado. Elígelo con `/output-style report` para tener cada respuesta con la forma del informe final: el resultado primero, después verificado, no verificado y pendiente, con HECHO, OPINIÓN e INFERENCIA marcados. Mantiene las instrucciones de programación de Claude Code (`keep-coding-instructions: true`).

## Instalación

```sh
npx finitemonkey init
```

O como plugin de Claude Code, desde dentro de una sesión. El plugin trae también el mod (la franja del control y los paneles dentro de Claude Code 2.1.287 o más nuevo):

```
/plugin marketplace add gabrielvieiraf/finitemonkey
/plugin install finitemonkey@finitemonkey
```

Requisitos: Node.js 20 o posterior, en Linux, macOS, Windows o WSL. La instalación hace copias de seguridad, fusiona en lugar de sobrescribir y se puede ejecutar dos veces sin romper nada. `doctor` te dice qué está mal y `uninstall` deja todo como estaba.

**Todavía más vago:** pídele a Claude Code "instala Finite Monkey siguiendo docs/AGENT-SETUP.es.md". La guía le indica al agente que ejecute los comandos él mismo, que te pregunte solo lo que sea decisión tuya y que nunca te pida un secreto.

Vista previa de la próxima versión: `npx finitemonkey@next init`, o `/plugin marketplace add gabrielvieiraf/finitemonkey#next` y después `/plugin install finitemonkey@finitemonkey-next`.

## De dónde viene el diseño

Finite Monkey parte de un estudio sobre lo que pasa cuando alguien trabaja con IA por encima de lo que puede juzgar. El ensayo [Efecto Rebote: el usuario como límite invisible de la inteligencia artificial](https://github.com/gabrielvieiraf/finitemonkey/blob/next/docs/ricochet/ricochet.es.md) describe dos fronteras que la persona no ve desde adentro: lo que no sabe pedir y lo que no puede evaluar, y muestra cómo cada mecanismo de aquí pone una verificación ejecutable en esos dos puntos.

El segundo ensayo, [La ilusión del segundo cerebro](https://github.com/gabrielvieiraf/finitemonkey/blob/next/docs/second-brain/second-brain.es.md), trata del conocimiento del proyecto: por qué los "segundos cerebros" con LLM y los archivos de contexto envejecen sin aviso, y cómo Finite Monkey trata cada afirmación sobre el código como artefacto de build, atada al hash del fragmento que describe y verificada al ejecutarla.

## ¿De verdad ayuda?

Claude Code solo contra Claude Code con Finite Monkey, en tareas con una trampa escondida que un modelo capaz deja pasar mientras dice que terminó: un reintento que cobra dos veces, el IVA redondeado sobre el total en lugar de por línea, un término de búsqueda que llega a la página como marcado, un refresh token que sobrevive al logout. Quien pide no domina el tema y aprueba lo que suena seguro. Mismo modelo (Sonnet), mismas semillas de tarea, 33 sesiones por brazo, plugin en la versión 0.1.0:

| | Claude Code | Claude Code + Finite Monkey |
|---|---|---|
| Dijo terminado sin estarlo | 9 de 33 (27%) | **3 de 33 (9%)** |
| Tarea correcta según la comprobación oculta | 17 de 33 | **23 de 33** |
| Dejó la trampa en el código | 10 de 33 | 10 de 33 |
| Costo mediano por tarea | US$ 0,04 | US$ 0,07 |
| Tiempo mediano por tarea | 27 s | 52 s |

El precio es cerca de 1,6 veces el costo y el doble del tiempo: el control ejecuta las comprobaciones que el agente se habría saltado. La trampa quedó en el código tanto con Finite Monkey como sin él en dos tipos de tarea: una migración de datos que corta nombres y rompe la versión anterior de la app durante un despliegue gradual, y respuestas de investigación hechas a partir de fuentes locales. La comprobación [`quotes`](https://github.com/gabrielvieiraf/finitemonkey/pull/438) del control ahora retiene la respuesta que cita mal sus propias fuentes. Método y desviaciones en [bench/PREREGISTRATION.md](https://github.com/gabrielvieiraf/finitemonkey/blob/next/bench/PREREGISTRATION.md) y [bench/DEVIATIONS.md](https://github.com/gabrielvieiraf/finitemonkey/blob/next/bench/DEVIATIONS.md).

## Preguntas frecuentes

Más preguntas en [docs/faq.es.md](https://github.com/gabrielvieiraf/finitemonkey/blob/next/docs/faq.es.md).

**¿Es un prompt?**
No. Son hooks y comprobaciones que se ejecutan aunque el modelo no se acuerde.

**¿Envía mi código a algún sitio?**
No. Tu código nunca sale de tu máquina y no hay telemetría. Sin que lo pidas, hace dos tipos de llamada de red: `gh` preguntando a GitHub por pull requests, solo si `gh` tiene sesión iniciada, y el nombre de un paquete enviado al registro de npm o de PyPI cuando un comando va a añadir un paquete que el proyecto no declara. La lista completa está en [Qué lee, escribe y envía](#qué-lee-escribe-y-envía).

**¿Me va a ralentizar?**
Las tareas pequeñas no tienen ceremonia, solo el control al final. Los hooks rápidos siguen siendo rápidos; la comprobación costosa va en `Stop`. El CI rechaza un pull request que lleve un guard de `PreToolUse` por encima de 50 ms en el p95 o que agregue contexto al inicio de la sesión; los límites están en [budgets.json](https://github.com/gabrielvieiraf/finitemonkey/blob/next/budgets.json).

**¿Y si bloquea algo que no debía?**
Abre una issue con la plantilla "Blocked something it should not have" (bloqueó algo que no debía). Los falsos positivos se tratan como bugs y se cuentan en público.

**¿Funciona con Codex, Cursor u otros agentes?**
Está hecho para Claude Code. El CLI, los git hooks y `ci gate` funcionan con cualquier agente, sin los hooks dentro de la sesión.

**¿Por qué "Finite Monkey"?**
El teorema de los infinitos monos dice que suficientes monos tecleando durante suficiente tiempo acabarían escribiendo Hamlet. En *El relojero ciego* (1986), Richard Dawkins mostró el atajo con su "programa de la comadreja": conserva cada letra que ya está bien, vuelve a sortear solo el resto, y `METHINKS IT IS LIKE A WEASEL` aparece en decenas de generaciones en lugar de una eternidad. El control funciona igual: lo que pasa queda fijado, y solo se reintenta lo que falla.

**¿Quién es el mono?**
Tú, y algunos días el agente.

# Preguntas frecuentes de Finite Monkey

[English](https://github.com/gabrielvieiraf/finitemonkey/blob/next/docs/faq.md) | [Português (Brasil)](https://github.com/gabrielvieiraf/finitemonkey/blob/next/docs/faq.pt-BR.md) | Español


## ¿Por qué Claude Code dice que terminó cuando no terminó?

Porque "listo" es una frase que escribe el modelo, y por defecto nada la comprueba. Es una queja frecuente, por ejemplo [anthropics/claude-code#60177](https://github.com/anthropics/claude-code/issues/60177) ("Claude marks tasks done without testing").

- **Hoy:** Claude Code tiene el hook `Stop`. Un hook escrito por ti puede negarse a cerrar la sesión y decirle a Claude por qué. Funciona, pero tú escribes y mantienes la comprobación.
- **En Finite Monkey:** una definición de terminado por tarea (comandos, tests, alcance) que el hook `Stop` ejecuta sobre los archivos actuales. Si falla, Claude recibe la lista de lo que falta y sigue trabajando. El informe final sale de esas pruebas, no del resumen del agente.

## ¿Cómo evito que Claude Code mienta sobre los tests?

Deja el resultado del test en manos de algo que no sea el agente. Una frase como "todos los tests pasan" en el chat, o un archivo de progreso que el agente edita, puede decir cualquier cosa. Una ejecución de tests que lanza un hook sobre los archivos actuales muestra lo que pasó de verdad.

- **Hoy:** un hook `Stop` que ejecuta tu comando de tests y bloquea si falla. Cuidado con las comprobaciones que aceptan cualquier comando que salga con 0, como `echo "tests passed"`.
- **En Finite Monkey:** solo cuenta como prueba lo que Finite Monkey ejecutó por sí mismo, sobre el estado actual del árbol. Los comandos triviales y las ejecuciones con cero tests se rechazan como prueba.

## Claude Code borró o se saltó mis tests para que pasaran. ¿Cómo lo evito?

Mira el diff además del resultado del test: después de borrar un test o marcarlo con `skip`, la ejecución sigue saliendo en verde.

- **Hoy:** revisa los diffs en archivos de test y añade un paso de CI que falle cuando baje el número de tests o aparezca `.skip` u `.only`.
- **En Finite Monkey:** un control de tests que detecta tests eliminados, `skip` u `only` nuevos, aserciones borradas y cambios en la configuración del propio control, también cuando el cambio llega por un comando de shell y no por una edición.

## Claude Code ejecutó `git reset --hard` y perdí trabajo. ¿Cómo lo evito?

Bloquea los comandos destructivos de git antes de que se ejecuten y guarda una instantánea de lo que se perdería. Es una queja habitual, por ejemplo [anthropics/claude-code#7232](https://github.com/anthropics/claude-code/issues/7232) y [#34327](https://github.com/anthropics/claude-code/issues/34327).

- **Hoy:** reglas de permiso `deny` para comandos destructivos de git en `.claude/settings.json`, o un hook `PreToolUse` que los bloquee. Los commits ya hechos suelen recuperarse con `git reflog`; los cambios sin commit, por lo general, no.
- **En Finite Monkey:** una instantánea antes de cada operación arriesgada de git, un `undo` que la recupera, worktrees con cambios pendientes archivados en lugar de borrados y una comprobación de "no se perdió nada" en cada merge.

## ¿Cómo evito que Claude Code haga force push?

Bloquéalo en dos sitios: en tu máquina y en el servidor.

- **Hoy:** una regla de permiso `deny` o un hook `PreToolUse` para `git push --force` y sus variantes, más protección de rama o un ruleset en GitHub que prohíba el force push en ramas compartidas. La regla del servidor es la que sigue valiendo si todo lo local se esquiva.
- **En Finite Monkey:** nunca hace force push y bloquea `--force` y sus variantes. También muestra qué reglas de git se cumplen por mecanismo y cuáles son solo texto.

## ¿Por qué Claude Code ignora CLAUDE.md, sobre todo después de la compactación?

Porque `CLAUDE.md` es texto cargado en el contexto del modelo, y nada lo ejecuta ni lo comprueba. El modelo lo pondera frente a todo lo demás de la conversación y puede dejarlo de lado. Mira [anthropics/claude-code#7777](https://github.com/anthropics/claude-code/issues/7777) y [#19471](https://github.com/anthropics/claude-code/issues/19471) ("CLAUDE.md instructions completely ignored after context compaction").

- **Hoy:** mantén `CLAUDE.md` corto y saca de la prosa toda regla que deba cumplirse siempre, llevándola a un hook, una regla de permiso, un git hook o un paso de CI.
- **En Finite Monkey:** hace ese traslado para las reglas que conoce y te muestra, regla por regla, cuáles se cumplen por mecanismo y cuáles siguen siendo solo texto.

## ¿Cómo hago que las reglas de CLAUDE.md se cumplan de verdad?

Convierte cada regla en el mecanismo más barato que pueda comprobarla. "Nunca hacer commit de `.env`" se convierte en un hook de pre-commit y un escaneo en CI. "Ejecutar los tests antes de decir listo" se convierte en un hook `Stop`. "No tocar producción" se convierte en un comando bloqueado.

- **Hoy:** hooks de Claude Code (`PreToolUse`, `PostToolUse`, `Stop`, `UserPromptSubmit` y otros), reglas de permiso, git hooks y CI. Cada uno se ejecuta aunque el modelo no recuerde la regla.
- **En Finite Monkey:** los entrega como un conjunto probado, instalado con copias de seguridad y que se quita con `uninstall`.

## ¿Cómo evito que Claude Code filtre claves de API o secretos en los commits?

Busca secretos en más de un punto, porque una clave puede filtrarse por un archivo escrito, un prompt, un commit, el historial o un pull request. [anthropics/claude-code#2142](https://github.com/anthropics/claude-code/issues/2142) es un caso de claves de API que llegaron al control de versiones.

- **Hoy:** un escáner de secretos en el pre-commit (gitleaks es una opción común), el secret scanning de GitHub con push protection y un hook `PreToolUse` o una regla `deny` que impida al agente leer archivos `.env`.
- **En Finite Monkey:** una única regla de detección, aplicada al escribir archivos, en los prompts, al hacer commit, en el historial y en CI. Un secreto encontrado se trata como un incidente para rotar. Los secretos se citan por archivo y línea, nunca por su valor.

## ¿Cómo evito que un agente de IA toque un servidor de producción?

No le des al agente un camino directo a producción y bloquea los comandos que lo crearían.

- **Hoy:** no dejes credenciales de producción donde el shell del agente pueda usarlas, despliega solo por CI y bloquea los comandos de shell remoto a servidores de producción con un hook o una regla de permiso.
- **En Finite Monkey:** los comandos con efecto sobre un servidor de producción declarado se bloquean. Producción cambia por el camino de despliegue que declaraste, y por ningún otro.

## ¿Qué es una definición de terminado para agentes de código?

Una lista de condiciones que una máquina puede comprobar antes de que el agente pueda dar el trabajo por terminado: comandos que deben salir bien, tests que deben existir y pasar, archivos que deben o no deben cambiar.

- **Hoy:** puedes escribir una a mano como script y llamarla desde un hook `Stop`.
- **En Finite Monkey:** crea una por tarea, la ejecuta en `Stop`, ata las pruebas al estado actual de los archivos y deja la ceremonia en cero para las tareas pequeñas.

## ¿Un hook Stop de Claude Code puede verificar los tests antes de terminar?

Sí. Un hook `Stop` puede ejecutar tu comando de tests y, si falla, bloquear el cierre con un motivo que Claude lee y sigue. Importan dos detalles: la comprobación debe ejecutarse sobre los archivos actuales, sin fiarse de una ejecución anterior, y no debe ceder la segunda vez que Claude intenta parar.

- **En Finite Monkey:** el control se construye justo sobre ese hook, con las reglas de prueba de arriba y un informe final de "no terminado" en lugar de un bucle infinito.

## ¿Hay un plugin de seguridad o guardrails para Claude Code?

Claude Code trae hooks y permisos, y un plugin puede unirlos en guardas que se cumplen aunque el modelo no recuerde la regla. Eso es Finite Monkey.

- **En Finite Monkey:** cubre cuatro daños ("listo" falso, secretos filtrados, cambios a mano en producción, trabajo perdido en git) con un control, una instalación y un `undo`.

## ¿Funciona con herramientas que cambian la cuenta de Claude Code cuando se acaba el límite?

Sí, si la herramienta lee un archivo de espera. Un supervisor que reinicia Claude Code en otra cuenta puede cortar la puerta en medio de un `Stop`, y la sesión reanudada te espera con el trabajo a medio revisar.

Para activarlo, agrega `supervisor:` con `enabled: true` a `.finitemonkey/config.yml` y haz que el supervisor defina `FINITEMONKEY_HOLD_DIR` con un directorio que vigile. Mientras la puerta corre o retiene la parada, Finite Monkey mantiene ahí `<sesión>.hold.json`, con una hora `until`; el supervisor no debe cambiar de cuenta mientras `until` esté en el futuro. El archivo vence solo (10 minutos para una ejecución, 15 para una parada retenida) y se borra cuando la puerta pasa. Cuando la sesión vuelve en la cuenta nueva, `SessionStart` le cuenta a Claude qué esperaba la puerta y la ejecuta otra vez. Los mensajes de reanudación que empiezan con `[supervisor]` no cuentan como tuyos, y un `usage.json` en el mismo directorio aparece en `finitemonkey gain`.

## Mi disco de WSL sigue grande después de quitar worktrees. ¿Finite Monkey lo reduce?

No, y no lo intenta: reducir el disco virtual de WSL 2 necesita derechos de administrador en Windows, así que sigue siendo un paso manual. `wt clean` y `wt archive` liberan el espacio dentro de Linux; Windows solo lo recupera después de compactar el disco.

1. Cierra todas las ventanas de WSL y ejecuta `wsl --shutdown` en PowerShell.
2. En PowerShell como administrador, ejecuta `Optimize-VHD -Path <ruta del ext4.vhdx> -Mode Full` (módulo Hyper-V), o `diskpart` con `select vdisk file="<ruta del ext4.vhdx>"`, `compact vdisk`.

El `ext4.vhdx` de una distribución está en `%LOCALAPPDATA%\Packages\<distribución>\LocalState\`.

# Instalar Finite Monkey para alguien (guía del agente)

Este archivo es para un agente de IA, como Claude Code, al que una persona le pidió instalar Finite Monkey en un proyecto. Las personas también pueden leerlo.

> **Estado: estable desde la 0.1.0.** `init`, `update`, `uninstall`, la compuerta, los bloqueos y el plugin de Claude Code salen en la dist-tag `latest` de npm; las vistas previas de la próxima versión salen en `next`.
>
> Válido para `finitemonkey` 0.1.0-next.40 o posterior. Comprueba la versión instalada antes de seguir cualquier paso posterior y detente si es menor.

## Conducta

1. **Ejecuta los comandos tú mismo.** No le pidas a la persona que escriba comandos que puedes ejecutar.
2. **Pregunta solo lo que es decisión suya.** Por ejemplo: qué idioma para los archivos generados, si se mantiene el estilo de commit del repositorio, si activar una función opcional. No preguntes lo que puedes averiguar leyendo el proyecto o la salida de los comandos.
3. **Nunca pidas secretos.** Ni contraseñas, ni claves de API, ni tokens, ni códigos de recuperación, tampoco "para terminar la configuración". Finite Monkey no necesita ninguno para instalarse.
4. **Prefiere `--json`.** Lee la salida JSON, no el texto para personas. Cuando exista el campo `next`, síguelo.
5. **No actives nada costoso sin preguntar.** Todo lo que gaste dinero, use APIs de pago, ejecute benchmarks largos, cambie configuración de GitHub (como los rulesets de ramas) o edite configuración global (`~/.claude/settings.json`, perfiles del shell) necesita antes un sí explícito de la persona.
6. **Explica cada paso en una o dos frases, en el idioma de la persona.**
7. **No edites archivos que gestiona `init`.** Si algo parece mal, ejecuta `doctor` e informa lo que diga.

## Dos formas de instalar

Las dos instalan los mismos hooks. Usa una o ambas: cuando el proyecto tiene sus propios hooks de Finite Monkey, los del plugin se hacen a un lado y nada se ejecuta dos veces.

1. **El plugin de Claude Code**, desde el marketplace de la rama `next`. Dentro de una sesión de Claude Code:

   ```
   /plugin marketplace add gabrielvieiraf/finitemonkey#next
   /plugin install finitemonkey@finitemonkey-next
   ```

   Cuando salga una versión estable, la rama por defecto tendrá su propio marketplace, llamado `finitemonkey` (`/plugin marketplace add gabrielvieiraf/finitemonkey`, luego `/plugin install finitemonkey@finitemonkey`). Puede convivir con `finitemonkey-next`, pero deja activo solo uno de los dos: ambos plugins se llaman `finitemonkey` y Claude Code se queda con un único conjunto de hooks. `doctor` falla y muestra el comando `claude plugin disable` cuando los dos están activos.

   El plugin trae los hooks y las skills (`task`, `verify`, `look`, `finish`) que Claude usa por su cuenta. Lleva su propia CLI (`scripts/finitemonkey.mjs`, el mismo build que la versión de su `plugin.json`), y cada hook ejecuta `node` sobre ese archivo: sin `npx` y sin descargas.

2. **`npx finitemonkey init`** en el proyecto (pasos abajo). Escribe en el proyecto los hooks, el piso de `permissions.deny` (más una regla `Read` de bloqueo por cada patrón de `.claudeignore`), reglas `ask` para los push a `main`/`master` y para comandos de publicación y despliegue, `permissions.blockReadsOutsideWorkingDirectories: true`, `.finitemonkey/config.yml`, una skill `verify` del proyecto (`.claude/skills/verify/SKILL.md`, que ejecuta la compuerta rápida antes de cada commit) y un bloque gestionado corto en `AGENTS.md`, que `CLAUDE.md` importa con `@AGENTS.md` (cada archivo se crea si no existe; todo lo que está fuera del bloque queda como estaba). Nunca define `defaultMode` ni `autoMode`, solo añade reglas que la configuración todavía no tiene y deja como está una skill `verify` que el proyecto ya tenga. Los hooks ejecutan `node` sobre `node_modules/finitemonkey` cuando el proyecto lo tiene como dependencia; si no, `init` copia la CLI que lo está ejecutando a `.finitemonkey/runtime/` (versionada, para que el equipo y las sesiones en la nube usen la misma versión) y los hooks ejecutan esa copia. Ningún hook llama a `npx`. Esto también vale donde los plugins no cargan (las sesiones en la nube de un repositorio leen el `.claude/settings.json` versionado). Añade `--marketplace` para registrar además el marketplace del plugin en la configuración del proyecto, para todos los que confíen en la carpeta; queda desactivado salvo que la persona lo pida. El marketplace sigue el canal de la versión en ejecución; `--channel next` o `--channel stable` elige uno.

## Qué obtiene la persona

Después de instalar, la persona no necesita recordar ningún comando. Finite Monkey trabaja con el contexto dentro de Claude Code: hooks en `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `Stop` y `SubagentStop`, y skills que Claude invoca solo según su descripción. Los comandos con barra son atajos opcionales. Al terminar, dile a la persona que siga trabajando como siempre.

## Pasos

### 1. Comprueba qué canal tiene versión

```sh
npm view finitemonkey dist-tags --json
```

- Si el comando falla, o ni `latest` ni `next` es `0.1.0-next.40` o posterior, no hay nada que instalar. Díselo a la persona y detente aquí.
- Si `latest` es `0.1.0` o posterior, usa `finitemonkey@latest` en los comandos de abajo.
- Si `latest` es `0.0.0` (solo reserva el nombre), solo el canal `next` tiene código. Dile a la persona: "El canal estable está vacío aquí. El canal `next` funciona, pero una versión nueva puede romper lo que hacía la anterior. ¿Lo instalo?" Sigue solo con un sí, usando `finitemonkey@next` en los comandos de abajo, tal como están escritos.

### 2. Comprueba el entorno

- Node.js 20 o posterior: `node --version`.
- El proyecto es un repositorio git: `git rev-parse --show-toplevel`.
- Estado del árbol: `git status --porcelain`. Si hay cambios sin commit, avisa a la persona y pregunta si continuar. `init` hace copias de seguridad, pero la persona debe saberlo.

### 3. Revisa el plan antes

```sh
npx finitemonkey@next init --dry-run --json
```

Esto lee el proyecto y devuelve el plan sin escribir nada: `data.actions` lista cada archivo con `create`, `merge`, `update`, `unchanged`, `keep-edited` o `skip-foreign`; `data.warnings` lista lo que la persona debe saber (otro plugin que también decide cuándo termina la sesión, un Claude Code demasiado antiguo para bloquear cuando un hook falla, un archivo que no es de Finite Monkey); y `data.diff` muestra el cambio exacto. Resume el plan para la persona en pocas líneas. Pregunta solo estas decisiones:

- Estilo de commit, solo cuando la salida diga que la mayoría de los commits recientes no sigue Conventional Commits: `--commits free` mantiene el estilo del repositorio, `--commits conventional` adopta el predeterminado. Los demás valores predeterminados valen para todos; el README lista cada uno con su evidencia, y cualquiera se apaga después en `config.yml`.
- Ejecutor de pruebas, linter y carpeta del código, solo cuando la salida liste `conventionQuestions` con estado `pending` (la función `defaults-adapt` está activa): `--tests vitest`, `--lint biome` o `--layout src` adoptan lo detectado, y `--tests off` (igual `--lint off`, `--layout off`) mantiene el predeterminado incorporado. Un estado `shadow` solo informa la detección; no se pregunta nada.
- Si registrar el marketplace del plugin en el proyecto (`--marketplace`).
- Si activar el sandbox de Claude Code para esta persona (`--sandbox`, solo macOS, Linux y WSL2). Va a `.claude/settings.local.json`, no a la configuración versionada: Claude Code se niega a arrancar sin el sandbox, los comandos en el sandbox no leen `~/.ssh`, `~/.aws` ni los `.env` del proyecto, y solo llegan a los hosts de `sandbox.hosts` en `config.yml` (npm y GitHub por defecto).
- Si revisar una vez las sesiones locales de Claude Code en este proyecto (`--look-back`). Lee los logs de sesión de esta máquina y muestra conteos estimados de lo que Finite Monkey habría bloqueado, con los secretos enmascarados. No se guarda ni se envía nada. Sin la opción, no se lee ningún log de sesión.

### 4. Instala

```sh
npx finitemonkey@next init --yes --json
```

Pasa las decisiones de la persona como flags (por ejemplo `--commits free --lang es`). Sin `--yes`, `init` sale con código 4, el plan y un campo `next` con el comando exacto para ejecutar cuando la persona esté de acuerdo. `init` guarda una copia de cada archivo que toca en `.finitemonkey/backups/<timestamp>/`, registra lo que escribió en `.finitemonkey/lock.json`, combina `.claude/settings.json` sin quitar ningún hook ni permiso de la persona, añade un bloque gestionado a `.gitignore` (el estado queda local, `config.yml` se versiona) y se puede ejecutar otra vez sin riesgo: una segunda ejecución sin cambios no escribe nada.

### 5. Verifica

```sh
npx finitemonkey@next doctor --json
```

Cada elemento tiene `check`, `status` y `fix`. Si alguno no está en `ok`, ejecuta el comando de `fix` cuando sea seguro y no caiga en la regla de conducta 5, y vuelve a ejecutar `doctor`. Informa lo que quede.

`npx finitemonkey@next doctor --fix` repara los archivos del proyecto que le pertenecen (hooks, reglas de deny, el bloque del `.gitignore`) con la misma copia de seguridad y el mismo bloqueo que `init`, y nunca toca los settings del usuario ni el perfil de la shell. Si el usuario quiere reportar un bug, `npx finitemonkey@next doctor --report` guarda un archivo Markdown enmascarado en `.finitemonkey/reports/` para adjuntarlo a la issue.

### 6. Cuéntaselo a la persona

En una o dos frases: qué se instaló, lo que `doctor` no pudo corregir y que ya puede seguir trabajando sin ningún comando nuevo.

## Códigos de salida

| Código | Significado |
|---|---|
| 0 | Éxito |
| 1 | Una comprobación falló |
| 2 | Error de uso |
| 3 | No configurado |
| 4 | Necesita a la persona (una decisión o una confirmación) |
| 5 | El propio Finite Monkey falló |

Con `--json`, los errores llegan como `{"schemaVersion":1,"error":{"code":"...","message":"...","fix":"..."}}`. Ejecuta o sugiere el comando de `fix`.

## Actualizar

```sh
npx finitemonkey@next update --check --json
npx finitemonkey@next update --yes --json
```

`--check` sale con 1 cuando los archivos gestionados difieren de esta versión y con 0 cuando coinciden. `update` fija los hooks en la versión nueva y renueva los archivos generados que la persona no editó. Cuando una versión nueva cambió el formato de un archivo gestionado, `update` también ejecuta la migración de esa versión, en orden de semver, sobre los archivos que la persona no editó. Un archivo generado que la persona editó se conserva, y la plantilla nueva o el texto migrado aparece en `data.diff` como propuesta. Un archivo que no se puede escribir por falta de permisos devuelve `install_permission_denied` con el `fix`.

## Deshacer

```sh
npx finitemonkey@next uninstall --yes --json
npx finitemonkey@next uninstall --yes --purge --json
```

El primero quita lo que Finite Monkey añadió y restaura las copias de seguridad, conservando `.finitemonkey/` (copias y evidencias). `--purge` borra también `.finitemonkey/`; después de `init` y `uninstall --purge`, el proyecto queda idéntico byte a byte a como estaba. Los archivos que la persona editó después de instalar se conservan y se listan en `data.kept`. Sin `--yes`, sale con 4 y el plan. El plugin, si está instalado, se quita aparte: `claude plugin uninstall finitemonkey@finitemonkey-next` (o `finitemonkey@finitemonkey` para el marketplace estable).
